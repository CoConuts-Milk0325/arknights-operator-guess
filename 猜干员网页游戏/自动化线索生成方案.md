# 自动化线索生成与随机游玩方案

## 1. 设计目标

用可复用的“能力事实 + 中文线索模板”生成题目，不维护固定题目列表。每局从当前可出题干员中抽取答案，再组合四条线索，对 431 名干员逐一检验，只有唯一解时才展示。网页离线运行，不调用 AI、网络接口或服务器。线索的真实含义优先于数量；数据规则扩充后，自然产生更多答案与组合。

有限的 431 名干员和有限事实不可能产生数学意义上无限个不同题目。这里的“无题库上限”是游戏无固定题单上限、可无限轮随机游玩，近期去重后允许再次出现旧组合。

## 2. 数据与配置模型

输入是 `干员文字资料/全体干员文字资料.json`。每个独立形态有稳定 ID、名称、星级、分支、精英阶段、技能、天赋、特性、模组、潜能与召唤物相关字段。星级以 1～6 星显示值存储。构建前需确认资料版本，并用 PRTS 核对有争议的机制。

常规配置定义为：**该形态最高合法精英阶段和等级 + 零潜能 + 一个最高合法等级技能 + 不装备模组或装备一个最高等级常规模组**。所有名称含“特限证章”的模组在配置枚举前整件排除，其效果不算干员能力。盘点普通攻击或被动能力时也可不指定技能。最高技能等级依星级和精英阶段而定，不能把低星级干员视为专三。特殊的“满潜费用”线索只在费用计算上切换到满潜，其余题目条件仍按默认口径。

事实应保存 `factId`、线索类别、主题、中文模板、适用成员、可能成员与来源证据。机制事实最好进一步保存 `witness`：具体技能、模组、天赋、触发条件和目标，供同条复合条件校验。将来新增规则时，对不明能力保留 `unknown`，不要仅凭未命中关键词推出 `false`。

## 3. 事实提取与语义

| 机制 | 允许形成的事实 | 核心审核点 |
| --- | --- | --- |
| 伤害 | 可造成的四种伤害、一种或两种、持续伤害 | 普攻类型、技能转换、天赋、模组、召唤物；治疗型普攻不计为物理伤害，不能靠未识别伤害词反推物理；依用户确认的本项目口径，对敌施加元素损伤计入元素伤害事实。 |
| 控制 | 可施加某种具名控制、无控制、具备某种数量类型控制 | 晕眩、停顿、束缚、冻结等不同名分别计；证据需包含对敌实际施加控制的动作。敌人已处于该状态、自身受控、免疫、解除或延长已有状态不能单独作为施加证据；两层寒冷触发冻结按 PRTS 规则计入。 |
| 攻击目标 | 真群攻、被阻挡条件限定的假群攻、技能最高等级的具体目标人数、普通攻击对空、无对空攻击能力 | 真群攻需要“所有敌人”“周围敌人”等范围全体受伤的明确证据；“阻挡的所有敌人”归入假群攻。普通攻击对空须能主动选取飞行目标，仅能攻击自身已阻挡的飞行单位不计；“无对空”按全部能造成伤害的能力判断，受击反伤也计入。锁定后实际攻击与额外攻击的目标计入同次攻击总数；极境式“停止攻击后仅锁定并施加状态”不计。无固定总人数的群攻与从多个初始目标分别链接的数量不得冒充“最多 N 名”。 |
| 范围与阻挡 | 扩大／缩小范围、两个以上技能打到原范围外、改变阻挡数 | 技能开关前后比较，注意侧方范围被收窄；“攻击范围内的目标获得增益”不是攻击范围扩大，装置自身的范围变化也不是干员本体的范围变化；不同技能的盘点允许分别取配置。 |
| 支援 | 多名其他干员的输出增益、其他干员的非回血生存增益、技力支援 | 明确受益目标；自身增益须写“自身”，不能用含混的“己方单位”代指其他干员；敌人受益或反向条件不能计入。 |
| 恢复 | 直接治疗、给无法被直接治疗的干员缓回 | 绝食可受生命回复类效果，不等同于普通治疗跳绿字；删除与“奶绝食”成员重复且题面过宽的 `heal:regen_other`。 |
| 削弱与自身能力 | 降低敌方防御、法抗、输出；普通／物理／法术／元素脆弱；自身闪避／护盾等 | 敌我对象必须清楚。普通脆弱增幅物理、法术、真实伤害，不能推出元素脆弱；技能、天赋与常规模组都应检查。 |
| 技能结构 | 自动／手动／被动触发、自动／攻击／受击回复技力、不同技能的回复方式 | 直接使用最高等级技能的结构化字段，复合条件由同一技能满足。 |
| 技能细节 | 连击、弹射、穿透、追加伤害、充能、弹药、再次使用变化 | 保留具体技能与最高等级描述，不能将单纯控制冒充攻击。 |
| 基础统计与数值 | 职业、分支、星级、分支覆盖的星级数、满潜费用位数、技能持续秒数／技力消耗／弹药量 | 可独立出题，每题合计最多一条。 |

“仅能”“没有”等排他限定若描述干员的能力全集，应对所有合法技能与常规模组配置求并集后判断。例如“仅能造成一种伤害且没有控制”和“可造成两种伤害类型与一种控制效果”都必须对全集成立；后者不再按某一技能／模组配置单独判定。题目明确盘点两个技能时可取两个不同技能，但每个技能所引用的模组须合法；不同线索彼此可引用不同配置。召唤物的对敌、对友效果计入干员能力；线索若写“自身生命／护盾／回复”等，主体必须是干员本体，不能借用召唤物或装置的状态。

## 4. 构建与出题算法

```text
对每名干员：
    读取最高合法阶段、最高技能等级与零潜能天赋
    排除所有特限证章，再枚举“不装模组”和每个可装备的最高等级常规模组
    为每个模组枚举技能配置，提取带见证的能力
    计算局部复合事实与全配置的排他事实

对每种事实：
    汇总确定满足者、可能满足者、目标证据
    缺少完整覆盖时，不把未发现者直接视为确定不满足

对每名潜在答案：
    搜索四条事实，约束主题去重、至少三类机制、统计／数值合计至多一条、复合类至多一条
    逐条按候选集合求交，保留未知者
    最终只剩该干员时，保存一组保底组合

浏览器开始新局：
    随机选择有保底组合的答案和四事实组合
    复查唯一解；搜索失败则用该答案的保底组合
    优先从当前周期未出过的答案中选题，并参考近期线索、线索主题与题目签名减少重复；公开线索与结算依据
```

原则上应使用三值事实：`true` 表示有证据，`false` 表示完整排除，`unknown` 表示资料或规则尚不足。唯一性筛选只删除明确 `false` 的候选。尤其特殊对空、召唤物、元素损伤爆发和全能力否定线索，不能因提取器未识别而排除竞争答案。线索自身必须为目标干员的 `true`，且证据可展示。

当前 `事实索引.js` 以 `members` 表示提取器确认的满足者。特殊对空事实用 `possibleMembers` 保留未审干员；伤害、控制的排他事实也用它保留召唤物能力未核准的干员。其余事实尚未普遍建立完整的三值审核矩阵，因此现阶段“唯一”是**按现有事实索引计算的唯一**。发布前仍需对实际题面逐项复核 PRTS；后续应把 `possibleMembers` 扩展到所有存在未判语义的事实，并保留规则版本与人工核查记录。

## 5. 线索组合质量

- 采用机制句式，不能只写“技能说明出现某词”。
- 一条线索可组合多个事实，但复合条件要有合法配置见证；复合类每题最多一条，基础统计与技能精确数值合计每题最多一条。
- 四条线索至少覆盖三类机制。由复合条件直接推出的较弱事实写入索引的 `implies` 字段；保底组合和浏览器随机组合都拒绝同题选择这对事实，避免把同义或直接推导的内容拆成两条占位。
- 优先选择涉及能力关系的线索；最终只有一个候选，最好是第四条线索才锁定答案。
- 线索不给技能专名或干员名；结算再展示技能、天赋、模组与本地档案来源。
- 随机种子、来源快照与规则版本共同用于重现和检查题目。近期题签只作体验优化，不是永久题库。

## 6. 现有实现与扩展顺序

现有 `生成游戏数据.py` 从档案产生 443 种事实，枚举技能与模组配置，并为全部 431 名干员找到唯一的四线索保底组合；网页在这些答案上继续随机搜索题目。全部 431 名干员都参加猜测和唯一性筛选。事实涵盖技能触发、技力回复、技能资源、持续时间、攻击与治疗方式、特性及天赋中的明确机制、同技能伤害与控制、目标优先级、召唤物、敌方属性变化及友方支援。精确秒数、技力和弹药数属于数值补充，每题合计只可出现一条。浏览器优先选择本轮尚未出题的答案，同时降低近期高频线索及主题再次出现的概率；答案池用完后再循环。对召唤物能力未核准的干员，排他事实会保留为可能满足，不能因未产生事实就从唯一性候选中删除；具体问题见[机制核对记录](机制核对记录.md)。

当前提取器包含关键词及正则启发式。提高覆盖和可信度的顺序：

1. 对当前 443 种事实建立 PRTS 语义核对表，记录适用范围、反例与规则版本；尤其审核否定、元素、召唤物、对空和“真群攻”。
2. 为所有事实增加三值候选信息，区分确认不满足与尚未判明；遇到未知时宁可少出题。
3. 给复合事实保存一套具体配置见证；对跨技能线索保存每个技能的独立见证，避免互斥模组混用。
4. 扩大机制分类与模板，再重新生成索引、答案池及保底组合。扩展分类不需要手工编写一整道题。

重新生成命令与离线使用方式见[使用说明](使用说明.md)。
